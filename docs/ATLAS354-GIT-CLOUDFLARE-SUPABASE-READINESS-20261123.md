## Production & development policy

Only `main` is published to GTAE's official public domain. Keep `development` for feature development and browser previews. Keep staging PR #98 private/nonproduction and integrate the latest verified production security baseline before proposing a new release. Release PRs to `main` require source/rights review, focused CI for changes, full browser + ZIP release gate when appropriate, and actual owner visual/iPhone Safari acceptance. A green Cloudflare deployment status alone does not prove public security.

**Public-code boundary:** The entire canonical GitHub repository is **public**, and any browser-delivered HTML/CSS/JS/images remain observable to visitors. The filtered Cloudflare `public/` output prevents directly serving internal `scripts/`, `docs/`, `.github/`, tests and GitHub build internals as website paths; it does not make the public GitHub repository or downloaded client-side scripts secret. Never commit private keys, service-role keys, confidential documents or privileged code to public GitHub. Do not switch repository visibility casually because it can break Git integration and current CI.

## Supabase / accounts — guest-first gates

Guest routes, maps, collectibles, Forge/Garage progress and export/import remain available without authentication. **Login remains disabled in the published `atlas-account.html`; the existing cloud-save repository in `atlas140-cloud-saves.js` is not connected to public UI.** An empty cloud-save table is NOT evidence that no Auth users exist; do not erase auth.users or sessions just because public signup isn't live. No public email addresses should be embedded or published until owner approves a working rights/contact mailbox.

Before optional private sync is enabled:
1. Verify Supabase Auth site URL and allow-listed redirect URLs **from the dashboard itself**; current GitHub documentation was historical and included the old `team-jura-atlas-preview.pages.dev` origin, which must be removed only **after** old project retirement and any guest export review. The Supabase connector did not expose live Auth provider/redirect settings in this audit; treat them as **unverified**.
2. Keep email verification on, anonymous/phone disabled unless separately needed, review signup/rate-limit/CAPTCHA settings, MFA account protections and secure project access. For passwords, enable leaked-password screening if available (Supabase Pro+) or consider a future verified passwordless email flow; no account should be enabled until custom SMTP/email delivery works.
3. Test user A vs user B with two *real* confirmed authenticated sessions and prove forbidden reads/writes return no cross-account data. The read-only RLS policy metadata inspection is **not** an end-to-end exploit test.
4. Require explicit per-category opt-in for first transfer from local guest saves; no automatic migration, preserve byte-exact raw backup, avoid overwriting existing cloud save on revision conflict; re-check Safari, Chromium and Edge.
5. Complete encrypted-in-transit HTTPS/Auth redirect testing, session lifecycle, logout, recovery, delete-account workflow, the proposed 14-day recovery policy (not implemented), and an incident plan before public account activation.
6. Do not publish Supabase `sb_secret_`, service-role keys, database credentials or authorization secrets. A **publishable** browser key is not a secret; its safety still depends on RLS/grants and verified project URL.
